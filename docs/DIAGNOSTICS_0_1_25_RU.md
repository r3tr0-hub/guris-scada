# Сбор диагностики на смену или сутки · 0.1.25

Запись включается автоматически вместе с основным процессом SCADA. Вход инженера, открытая страница «Производство» и нажатие кнопки записи не требуются. Закрытие окна в трей сохраняет запись; выход из программы останавливает её. Сервер предприятия, интернет и дополнительные программы на станке не нужны.

## Обновление

1. Полностью завершите прежнюю SCADA через её кнопку выхода или меню значка в трее. Не оставляйте две версии на одном ПЛК.
2. Распакуйте новый архив целиком **в отдельную папку на локальном диске**. Сохраните прежнюю папку для возврата.
3. До запуска скопируйте из прежней папки `connection.json`, **весь каталог `local`** и свои мануалы в `manuals`. Так сохранятся PIN, настройки, производственная история и журналы возврата таймеров. Не переносите старые `ui`, EXE и скрипты поверх новой сборки.
4. Запустите `Start_Compatibility.cmd`. Убедитесь в наличии связи с ПЛК и версии 0.1.25 на странице описания SCADA.
5. Войдите инженером → «Меню» → «Опции SCADA». В блоке **«Диагностический пакет»** должно быть «Диагностика записывается» и ноль пропусков.

Сборка поставляется с выключенным примером подключения. Перенос прежнего `connection.json` сохраняет действующее подключение. Новая установка настраивается инженером, как раньше. Новая диагностическая БД создаётся отдельно и не меняет схему существующей производственной БД. При возврате старой версии новая БД просто не используется.

## Как собрать 12 или 24 часа

1. Работайте на станке в обычном порядке. Можно вернуться в профиль оператора.
2. Оставьте ПК включённым и SCADA работающей 12 или 24 часа. Уберите переход Windows в сон и гибернацию на время сбора. Выключение только монитора допустимо. Рекомендуется иметь не менее **2 ГБ свободного места** для БД, временной выгрузки и запаса.
3. После смены войдите инженером → «Меню» → «Опции SCADA» → **«Последние 12 часов»** или **«Последние 24 часа»**.
4. Дождитесь сообщения о сохранении пакета. Опрос и запись продолжаются во время подготовки. Edge сохраняет `GurisSCADA_Diagnostics_…zip` в свою обычную папку загрузок Windows. При настройке запроса места сохранения выберите папку.
5. Отправьте **весь ZIP**. Не выбирайте из него один JSON и не редактируйте таблицы в Excel. Желательно кратко указать, какое поведение на станке показалось неправильным и примерное местное время.

Кнопки выгружают скользящий период назад от нажатия. Они не запускают отложенную запись и не требуют оставлять инженерный профиль открытым. Если после обновления прошло только два часа, в пакете будет два часа; недостающая история явно отмечена. Текущее накопление не стирается после выгрузки. Повторная выгрузка создаёт новый пакет.

## Что записывается

| Данные | Точность и источник |
|---|---|
| Состояние машины, автоматический режим, все три счётчика | Каждый уже полученный основной снимок ADS; обычно около 100 мс при исправной связи. Возраст и качество каждого значения сохраняются. Это частота наблюдений SCADA, не трассировка цикла ПЛК. |
| Аварии | Активные причины из штатного опроса, изменения списка и его качество. Если активных причин больше 24, трасса отмечает усечение; причина по материалу берётся из полного уже полученного списка. |
| Размотчик | Наблюдаемое разрешение автоостанова, конфигурация наличия датчика, режим временного/постоянного отключения, срок таймера. Конфигурация датчика **не равна физическому входу датчика**. |
| Очистка конвейера | Активность, ожидающий возврат и срок таймера. |
| Параметры | Каждые 30 секунд снимок кэша 256 основных полей и уже прочитанных инженерных полей: значение, качество, возраст, ошибка ADS и сырые байты. Открытая страница I/O попадает в тот же снимок. |
| Команды и записи SCADA | Постановка в очередь, отправка, результат обратного чтения, неизвестный результат, отказ, исходные/запрашиваемые байты, идентификатор операции и роль. Внешнее изменение в HMI отмечается как наблюдение; автор ему не придумывается. |
| Производство | Интервалы работы, остановки, ручного режима и отсутствия достоверных данных; назначенные причины и доказательства; решения текущего алгоритма и закрытие эпизода при первом состоянии работы. |
| Диагностика | Сеансы процесса, разрывы наблюдения, изменения часов, версия символов, длительность опроса, ошибки интерфейса, очередь/пропуски записи, версия и идентификатор исходников, ОС/ресурсы Windows и браузер при выгрузке. |

Открытие диагностики не создаёт ни одной дополнительной ADS-записи или ADS-чтения. Дополнительные инженерные поля и I/O продолжают опрашиваться только по прежним подпискам. Короткий импульс физического входа между опросами SCADA может остаться незамеченным. Периодический контекст не является историей каждого изменения всех 714 полей.

## Состав ZIP

| Файл | Назначение |
|---|---|
| `manifest.json` | Период запроса, доступные границы истории, версии, количество строк, пропуски, состояние записи и границы согласованных снимков. |
| `snapshot.json` | Расширенный текущий отчёт JSON, совместимый с прежними основными полями. |
| `trace.csv` | Наблюдения ключевых сигналов, временные метки, качество, счётчики, таймеры. Разделитель `;`. |
| `events.jsonl` | События диагностики и команд; один JSON на строку. |
| `context.jsonl` | Периодические снимки параметров из кэша. |
| `sessions.csv` | Запуски, завершения, пропуски и ошибки хранения. У текущего сеанса конец ещё пустой. У старого сеанса пустой конец означает, что штатное завершение не было записано. |
| `production_intervals.csv`, `production_events.jsonl` | Производственная история с объяснениями простоев. |
| `audit_current_session.csv` | Прежний CSV операций текущего запуска; операции прежних записанных запусков остаются в `events.jsonl`. |
| `field_catalog.csv`, `alarm_catalog.json`, `README.txt` | Справочники привязок и описание формата. |

В сеансах и текущем отчёте также сохранено смещение местного времени относительно UTC. Временные метки UTC заданы миллисекундами Unix; монотонные метки сравниваются **внутри одного сеанса**. В начале периода добавляется 10 минут контекста и последнее предшествующее наблюдение, если они доступны. Обе исторические БД читаются в собственных транзакциях SQLite; текущий JSON снимается отдельно и не обещает единого атомарного снимка с обеими БД. ZIP содержит CRC32 каждого файла для обнаружения повреждения при передаче.

В пакет не включаются `accounts.json`, хеши PIN, браузерный профиль и файлы с токенами сессии. Тексты ошибок UI очищаются от длинных цифровых вводов и токенов. Пакет всё же содержит рабочие параметры, адрес ПЛК и производственную информацию — это данные для инженера и анализа.

## Хранение и ограничения

Запись ведёт отдельный поток в `local/diagnostics.sqlite`, через ограниченную очередь в памяти. ADS-поток не ждёт SQLite или сжатия ZIP. После заполнения очереди теряются старейшие ожидающие записи, а число пропусков растёт. Ошибка диска отображается в состоянии диагностики; управление продолжает работать. После устранения ошибки запись возобновляется, но утраченный участок не восстанавливается.

История ограничена возрастом 72 часа, 1 200 000 наблюдений и размером основной БД 512 МиБ; применяется первое достигнутое ограничение. При обычном опросе 100 мс предел строк соответствует примерно 33 часам. Поэтому выгружайте сутки вскоре после завершения сбора. WAL и временные файлы выгрузки требуют дополнительного места. Смена часов Windows может нарушить календарные границы отбора — расхождение с монотонным временем видно в событиях. Исчезновение питания не позволяет гарантировать сохранение последних ещё не записанных данных.

**Алгоритм причин простоев остался версии 1.** Короткое доматывание по-прежнему закрывает прежний эпизод. Этот выпуск собирает доказательства для последующей корректировки, не переименовывает существующие простои в «замену рулона» автоматически.

Если ZIP сформировать не удалось, сохраните «Снимок состояния · JSON» и отчёт `Run_SCADA_Check.cmd`; каталог `local` сохраните для последующего восстановления.

Для предварительной проверки ZIP на отдельном ПК с Python 3 можно выполнить:

```sh
python tools/analyze_diagnostics.py GurisSCADA_Diagnostics_24h_....zip
```

Скрипт читает архив без изменения и выводит JSON: полнота, разрывы, плохое качество, перезапуски, результаты команд и кандидаты на цепочку «материальная причина → короткая работа → неразмеченный простой». Кандидаты требуют разбора; они не подтверждают замену материала.
