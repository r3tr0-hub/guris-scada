# Производство — SCADA 0.1.21

## Где открыть

«Производство» занимает место «Мануалов» в левой панели перед «Авариями» и показывает только работу и простои. «Задания» — отдельная страница: вход через нижнюю плашку «Текущее задание» на главной. Оператору доступна очередь и всё содержимое ТЗ, но импорт, выгрузка и действия учёта доступны инженеру. В простоях оператору показана только сводка текущей смены 08–20 / 20–08: работа, простой и обзорная лента. Ручной режим входит в простой; отсутствие наблюдений не считается подтверждённым простоем. Подробные периоды, фильтры, действия учёта и экспорт защищены инженерной авторизацией в API. Нажатие на состояние машины открывает историю. Мануалы доступны через блок времени/даты → «Мануалы». Скрытие кнопки выхода не скрывает мануалы.

## Начать работу с заданиями без сервера

1. На отдельном ПК откройте `tools/Constructor_TZ_SCADA.html` из архива в браузере. Интернет не требуется.
2. Заполните изделие и упаковку, номер ТЗ, редакцию, тираж, утверждающего, дату утверждения и номер производственного задания. При необходимости укажите срок.
3. Нажмите «Задание для SCADA». Будет сохранён JSON со снимком исходных данных, справочников, расчётов веса, допусков и паллетирования. Печать/PDF и Excel сохранены.
4. На станочном ПК войдите инженером → «Главная» → «Текущее задание» → «Загрузить задание» → выберите JSON.
5. Инженер выбирает задание и подтверждает «Начать задание». Кнопки приостановки и завершения меняют только учёт: запуск, остановка и настройки ПЛК через них не выполняются.

Для проверки предусмотрены два файла в `production/examples`: `example_100x150.json` и `example_500x600.json`. Это примеры, не утверждённые задания предприятия. Они не загружаются автоматически.

Карточка содержит изделие с векторным чертежом, материалы, упаковку, схему яруса паллеты, расчётные нормы веса и требования. Значения из ТЗ не преобразуются автоматически в настройки станка. Спецификация — описание изделия; задание — отдельный тираж, срок и ход исполнения.

Повторная загрузка того же файла не дублирует задание. Изменённый документ с прежним id отклоняется. Конструктор сохраняет id при повторной выгрузке неизменённого документа; при изменении данных создаёт новый id. Для изменённого ТЗ указывайте новую редакцию. Поле «Утверждает» и дата являются реквизитами документа, а не проверенной электронной подписью.

## Учёт выпуска

Выпуск суммируется по положительным изменениям `MAIN.diToplamAdet` во время активного задания. Приостановка исключает последующий выпуск из этого задания до продолжения. Выполнение плана и штатная остановка станка не закрывают задание автоматически. Одновременно активно одно задание; приостановленное можно продолжить позже.

Сброс, пропажа показаний, смена ADS-сессии/подключения, переполнение очереди наблюдений и перезапуск приводят к отметке «Учёт может быть неполным». Неподтверждённые изменения через такой разрыв не прибавляются. После получения новой исходной точки последующие изменения учитываются. Положительные пакетные обновления счётчика принимаются без вымышленного ограничения по скорости ножа.

Показан наблюдаемый выпуск по счётчику, не количество годных пакетов и не складской учёт. Обнуление счётчиков остаётся доступно по прежним правилам. На границах начала/завершения действует разрешение опроса; программно восстановить продукцию, потерянную самим счётчиком при сбросе, нельзя.

## История работы и остановок

Есть выбор дня, вчерашнего дня, 24 часов, часа, 15 минут, текущей смены или собственного периода до 31 дня. Можно отфильтровать состояние и задание. Итоги показывают отдельно работу, остановки, ручные движения/референс и отсутствие данных. Лента обзорная, с преобладающим состоянием в каждом из 480 временных участков; точные исходные интервалы доступны инженеру в прокручиваемом списке и детализации. Список догружается порциями по 100, до 2000 строк на экране; полный период доступен в экспорте. Лента не изменяет исходную историю. При чтении списка сохраняется позиция; доступна кнопка обновления. Лента масштабируется +/− с перемещением пальцем/мышью. Увеличенный участок заново разбивается на 480 временных отрезков; минимальное окно — минута. Итоги относятся к целому периоду, масштаб не меняет учёт.

Период «Текущая смена · 08/20» использует уже применяемую в часах схему 08:00–20:00 / 20:00–08:00 по времени станочного ПК. Для оператора это единственный период; его границы вычисляет нативный процесс по часам станочного ПК. Инженеру доступен также произвольный период. OEE, плановые/внеплановые потери и брак не рассчитываются без соответствующих исходных данных.

Классификация опирается на `.I_MESSAGEID` и `MAIN.BSISTEMOTOMATIK`: 4/7 при включённой автоматике — работа; 6/12 — JOG/референс; остальные известные состояния — остановка, кроме противоречивых сочетаний автоматики и готовности, которые обозначаются как отсутствие данных. Исходный код сохраняется. Это состояния штатной автоматики, а не измеренная скорость осей; технологические паузы внутри автоматического цикла отдельно не размечаются. Очень короткие изменения между опросами могут быть не замечены; для гарантированного учёта каждого такого изменения нужен журнал переходов со стороны ПЛК.

Потеря связи, зависание наблюдения и выключенная SCADA не считаются подтверждённой остановкой. При потере данных достоверный интервал заканчивается последним подтверждённым наблюдением; неопределённый хвост получает «Нет данных». После перезапуска между сохранённой границей и новым запуском создаётся такой же промежуток. Время — UTC в миллисекундах, отображение — местное время ПК; длительности в процессе вычисляются по монотонным часам. Перевод системных часов выделяется событием, не создавая отрицательных длительностей.

В детализации есть связанные аварии, код состояния и задание. По новым активным условиям аварий 14/15/28/29/67/68 назначается предположение «Замена лайнера», по 27 — «Замена рулона». Окно связи с остановкой — ±2 секунды; причина сохраняется до следующего наблюдаемого запуска. Старые предупреждения, конкурирующие признаки, разрывы наблюдения и остальные аварии причины не назначают. Причины и комментарии в SCADA не редактируются; неподтверждённая причина отмечена как автоматическое предположение. Подробные правила и доказательства — в `CHANGES_0_1_20_RU.md` и `MENU_PRODUCTION_EVIDENCE_0_1_20.json`.

## Хранение, обновление и резервная копия

SQLite встроена в EXE, отдельная установка не нужна. База: `local/production.sqlite`, схема 2. Добавление `stop_causes` сохраняет прежние интервалы, задания и заметки; старые записи не получают причин задним числом. Запись идёт в отдельном потоке; ADS только передаёт снимки в ограниченную очередь. Изменения записываются транзакциями примерно раз в 500 мс, действия по заданиям — до положительного ответа. При аварийном завершении последняя незаписанная часть становится неопределённой; задание помечается как неполное. Чтение страниц и закрытие окна в трей не останавливают сбор.

Режим WAL, `synchronous=FULL`, проверка базы при запуске. Основная база ограничена примерно 1 ГиБ; события не удаляются автоматически без подтверждения будущего сервера. При ошибке записи выводится сообщение, новые операции учёта блокируются; управление станком продолжает работать. После устранения причины ошибки перезапустите SCADA. Тихого удаления истории и автоматического создания новой базы поверх повреждённой нет.

До 5000 локальных заданий, в очереди показаны первые 500 по состоянию, приоритету и времени. Старая история и документы сохраняются в базе. Экспорт охватывает выбранный период и включает исходные события, точные интервалы и полные документы связанных заданий.

Каталог `local` переносите только при обновлении того же станочного ПК. Для другой линии требуется собственная идентичность машины и отдельная история.

При обновлении: полностью завершите SCADA, распакуйте новую сборку отдельно, перенесите прежние `connection.json`, весь `local` и свои `manuals`. Для резервной копии базы тоже полностью завершите программу и копируйте весь `local`, включая имеющиеся `production.sqlite-wal` и `production.sqlite-shm`. Нельзя переносить только EXE без файлов `ui`.

## Подготовка будущего сервера

Серверный адрес и рабочий API предприятия пока не предоставлены; внешних сетевых обращений нового модуля нет. Интерфейс честно показывает «сервер не подключён». Подготовлены неизменяемые документы заданий, постоянный machineId, последовательность событий и их устойчивые id вида `machineId-sequence` для устранения дублей при будущей синхронизации.

Локальные API требуют штатный токен интерфейса и проверку Host/Origin; они не открыты для сети предприятия:

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/api/production` | Инженер: очередь и текущий выбор; оператор: только краткая карточка текущего задания |
| GET | `/api/production/shift` | Итоги текущей смены и лента, без интервалов/аварий; оператору доступен только этот обзор |
| POST | `/api/production/import` | Один JSON задания, только инженер |
| POST | `/api/production/action` | Только инженер; `id`, `action`: `start`/`pause`/`finish`, уникальный `operationId`; повтор того же действия не дублируется |
| GET | `/api/production/job/{id}` | Оператор и инженер; полный неизменяемый документ и ход исполнения |
| GET | `/api/production/history?from=…&to=…&offset=0&kind=all&job=…` | Только инженер; UTC-миллисекунды; до 31 дня, точные интервалы, итоги и обзор |
| GET | `/api/production/interval/{id}` | Только инженер; детализация одного интервала |
| GET | `/api/production/export?after=0` | Только инженер; события по 20; `nextAfter` и `hasMore`, дополнительно фильтр `from`/`to` |

`viewFrom` / `viewTo` задают увеличенный участок ленты внутри основного периода. Для `/shift` другие параметры отклоняются, а границы участка должны находиться внутри текущей смены. Автоматическая причина имеет поля `reasonSource=automatic`, `reasonCode`, `reasonAlarms`, `reasonDetectedAt`; отдельная таблица не меняет исходные коды состояния. Событие `downtime.reason_inferred` сохраняет основание назначения. Подтверждённая серверная заметка имеет приоритет.

Формат задания описан в `production/job.schema.json`. Открытые интервалы доступны в истории; событие `interval.closed` появляется при закрытии. Полученные сервером данные потребуют отдельного времени приёма. Подтверждения доставки, авторизация серверного соединения, загрузка причин с историей правок и рабочий серверный адаптер подключаются после согласования API. Схема хранения заметок предусмотрена, редактора на станке нет. Экспорт файла не считается подтверждением сервера и не удаляет события.
