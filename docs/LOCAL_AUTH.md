# Local identity provider and a later enterprise server

0.1.6 exposes a stable identity contract: provider=local, userId=local-operator or local-engineer, and role=operator/engineer. The browser never supplies a trusted role. The HTTP boundary resolves a native session and checks permission for /api/options, /api/connect and /api/auth/password. PLC production settings, zero-only counter resets and timed belt boost retain their independent device/state/type/readback checks for both roles.

The common operator profile requires no password. The engineer profile is initialized explicitly at first local login, with a user-chosen password; no shared factory password or master password is shipped. Native Windows CNG derives PBKDF2-HMAC-SHA256 (600000 rounds, random 16-byte salt, 32-byte key); OpenSSL implements the identical derivation only for the Linux test host. Credential files use atomic flush/replace. Malformed existing credentials lock bootstrap rather than silently resetting it.

In 0.1.8 new and replacement engineer passwords must contain 6–128 ASCII digits. They are strings, so leading zeros matter. This policy is checked natively for setup and password changes. Existing 0.1.7 hashes, including letter/Unicode passwords, still work at login and as the current password during replacement. No automatic password reset or plaintext migration is performed. The touch keypad masks input and clears its draft on close. A physical PC keyboard can enter an existing letter password in the same dialog.

The file is `local/accounts.json` alongside the EXE directory, with four keys: `version` (1), `iterations` (600000), `salt` (32 hexadecimal characters encoding 16 random bytes), and `hash` (64 hexadecimal characters encoding a 32-byte PBKDF2 result). No plaintext password, PIN, reversible ciphertext or factory password is stored. Password changes generate a fresh salt and key, save atomically and rotate the session. The frontend discards polling responses that began before/during an identity change, then refreshes identity with the new cookie, so an old-cookie response cannot accidentally navigate away from engineering settings.

A fresh 256-bit session is generated after engineering login, held in an HttpOnly/SameSite=Strict cookie, and expires after 8 hours. Restart, operator selection and password changes revoke old sessions. The server binds loopback, validates Host/Origin and the existing random application/CSRF token. Passwords and session tokens are absent from device reports and audit logs. Native permissions do not prevent an OS administrator from changing local files; use Windows file permissions and controlled backups for that boundary.

In 0.1.9 the primary Windows UI uses Edge's private kiosk session. Closing the entire private browser session drops its cookie; opening the UI again requires engineer sign-in. The credential hash, selected language, application options and timed-belt journal remain native local files. This does not change the native 8-hour maximum, revocation checks or PLC transaction permissions. Ordinary-browser diagnostic mode remains available separately.

The local provider is isolated in src/local.h; HTTP permission checks are centralized in src/http.h. Production transactions record the resolved stable actor ID; automatic speed recovery uses scada-timer. The frontend uses returned identity/capability flags and is not the authorization authority.

For an enterprise server, keep this role/permission contract and replace the local credential/session provider with an authenticated server adapter. Introduce unique employee IDs, server-issued identities, role assignments and a documented offline sign-in policy; common role names must not substitute for employee identity. Validate server tokens in the native application with issuer/audience/expiry and revocation policy, over authenticated TLS. Do not upload local password hashes or trust a role passed from browser JSON. Centralize audit events with machine identity and stable transaction IDs, leaving PLC operations and recovery deadlines local unless the machine program itself is changed.

No server requests, cloud login, mock corporate account or network fallback is implemented in 0.1.6. The current application runs locally.

Primary references: [Microsoft BCryptDeriveKeyPBKDF2](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptderivekeypbkdf2), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
